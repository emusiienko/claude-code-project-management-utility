# ADR-032: MCP surface path-versioned under `/mcp/<version>`

**Date**: 2026-09-30
**Status**: Accepted
**Decision**: The MCP surface is path-versioned. Each MCP version is served by its own MCP server instance, mounted at `/mcp/<version>` on the shared backend app. The only version today is `v1`, so MCP clients connect at exactly `http://<host>:<port>/mcp/v1` (`http://localhost:8000/mcp/v1` on the prod stack, `:8100` on the dev stack). This parallels REST's `/v1` base path. A new MCP version is a new server instance under a new path segment, never a change to an existing one. This refines ADR-007 and does not supersede it. ADR-007's topology stands unchanged: MCP is path-mounted on the same app, process, and port as REST, and its namespace stays disjoint from the REST route space. ADR-007 wrote its path only as an example ("e.g. `/mcp`"). This ADR fixes the concrete address.
**Options Considered**:
- Bare `/mcp`, unversioned: the literal reading of ADR-007's example, also stated in the API Contract (as an example) and the root README.
- `/mcp/v1`, one server instance per version under `/mcp/<version>` (chosen): the path the backend code, Code Map, and Coding Conventions already described, and the one confirmed with the user in SESSION-011.
**Rationale**: It matches the versioning scheme the service already uses. REST is path-versioned under `/v1`, and a bare `/mcp` would be the only unversioned surface. One instance per version lets a future breaking change to tool names or payloads ship beside the old version instead of breaking every agent at once. No working client depended on bare `/mcp`. Before STORY-011 the only reachable route was `/mcp/v1/mcp`, and it failed with a server error because the MCP session manager never started, so choosing `/mcp/v1` broke nothing. Choosing `/mcp` would have meant a second code change for no benefit. `/mcp/v1` still satisfies ADR-007: same port, and inside a `/mcp` namespace that stays clear of REST's `/v1`.
**Trade-offs**: Clients must configure the versioned URL, and a version bump means every client changes its URL on purpose, with no silent upgrade. Running two MCP versions side by side means two server instances in one process, all sharing one service layer. That cost is accepted if it ever happens, and it hasn't yet. Each mounted MCP instance's lifecycle must also run inside the backend app's own, or the mount answers but fails every request. That is a backend-internal wiring concern and isn't restated here.
