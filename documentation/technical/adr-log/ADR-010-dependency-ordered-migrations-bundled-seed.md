# ADR-010: Dependency-ordered migrations, root-table-first, inline FKs, seed bundled with its schema revision

**Date**: 2026-07-06
**Status**: Accepted
**Decision**: The Alembic migration chain is authored in **dependency order**: a table is created only after every table it references already exists. The root entity `project` is the first revision (`0001_project`, `down_revision = None`); child tables that reference it come later. Each table declares its foreign keys **inline** toward already-existing parent tables (`ForeignKeyConstraint([...], ["project.id"], ondelete="CASCADE")`) — no deferred FK, no `batch_alter_table`, no table rebuild. Each schema revision **bundles its own seed data** in the same `upgrade()` (via `op.bulk_insert` with fixed UUIDs and deterministic timestamps), rather than in a separate seed-only revision. Under STORY-003 the chain was collapsed to two revisions: `0001_project` (project table + one "Test Project" seed row) and `0002_settings` (`system_settings` + `project_settings` with the inline `project_settings → project` FK, plus the six default dictionaries seed).

This licence extended to **rewriting** the previously-shipped chain (`0001_baseline`, `0002_settings_schema`, `0003_settings_seed`) rather than patching it append-only, because that chain had **never been successfully applied** — the first PostgreSQL deployment failed at `CREATE TABLE project_settings` when its FK targeted a non-existent `project` table. With no deployed database and no data to preserve, the append-only migration discipline did not apply, so the cause was fixed directly.

**Options Considered**:
- Dependency-ordered chain, root-first, inline FKs, seed bundled per schema revision (chosen)
- Patch the broken chain append-only with a new revision adding `project` and a deferred/`batch_alter_table` FK on `project_settings`
- Keep seed data in dedicated seed-only revisions separate from schema DDL (the prior ADR-009 approach)

**Rationale**: The broken deployment was caused purely by ordering — a child table was created before its parent. Creating the root table first makes every future FK point "upward" to a table that already exists, so the inline FK resolves on both SQLite and PostgreSQL with no dialect branching and no deferred-constraint machinery. Bundling seed with the schema revision that introduces the table keeps "the table and the data that makes it immediately usable" atomic and co-located, so a fresh `alembic upgrade head` yields a usable database in one coherent step per table. Rewriting (rather than patching) was safe and simpler because the chain had never run — there was literally no state to migrate. This establishes the house rule for all later inter-domain FKs (stories → tasks → attachments/comments/links, milestone joins).

**Trade-offs**: Rewriting a migration chain is only ever permissible while it has never been applied to any real database; once a chain is deployed, the append-only discipline returns and this ADR's "rewrite" licence no longer applies. Bundling seed into the schema revision means a seed-value change requires a new migration touching that revision's lineage rather than editing an isolated seed revision — accepted, as seed changes are infrequent and benefit from migration history. Seed values remain duplicated between the migration and the architecture document (the canonical list) and must be kept consistent by review. Supersedes ADR-009, whose separate-seed-revision structure and pre-`project` `project_settings` creation are replaced by this chain.
