# ADR-026: Session project ownership + fixed non-dictionary status lifecycle enum

**Date**: 2026-07-30
**Status**: Accepted

**Decision**: A session belongs to **exactly one project** (a required non-null `project_id` FK, `ON DELETE CASCADE`) and every session read — the paginated list and the unfinished-sessions query alike — is scoped to a single project; there is no cross-project session listing or cross-project incomplete query. A session's lifecycle is a single required **`status` enum with exactly three fixed values** — `pending` (default at creation, never a create input) → `in-progress` → `finished` — settable to any value in any direction on update, with no transition order enforced. The enum is validated at the **schema layer** and is deliberately **not** dictionary-validated (unlike `task_statuses` / `story_statuses`), so it is neither configurable per project nor stored in the settings dictionaries. "Incomplete" everywhere means `status` is `pending` or `in-progress`; "complete" means `finished`. `status` is fully decoupled from `result_decisions` / `result_summary` — a session can be `finished` with neither result set, or `pending` / `in-progress` with both set. `topic`, `goal`, `participant_role`, and `status` are mandatory and non-clearable; `participant_role` is validated against the project's effective `participant_roles` dictionary. This is a **contract revision to v1.8** for the Sessions domain only; every other domain's contract is unchanged.

**Options Considered**:
- **v1.0 forward-spec shape** (project-less sessions; completion *derived* from `result_decisions` / `result_summary` both being null; free-form `status` string; `topic` immutable): the shape carried in the LOCKED v1.0 contract and the original `architecture.md` session row.
- **Interim `is_complete` boolean + free-form `status` string** (SESSION-021): an explicit completion boolean decoupled from the result fields, alongside a separate free-form status label. Built in TASK-001/002/003, then retired before acceptance.
- **Fixed three-value `status` enum, project-scoped, not dictionary-validated** (chosen): one required lifecycle column carrying both "where is this session in its life" and "is it finished," scoped to an owning project.
- **Dictionary-validated session status** (a per-project `session_statuses` dictionary, mirroring `task_statuses` / `story_statuses`): rejected — see Rationale.

**Rationale**:
- **Project scope matches the real read pattern.** The orchestrator's cross-restart continuity question is always asked *of a chosen project* ("are there sessions I opened in this project that were never concluded?"), exactly as Task Manager scopes stories and tasks to one active project. A cross-project session firehose was a generality the product never needed; requiring `project_id` makes every session read a simple indexed, project-scoped query and lets project deletion cascade its sessions like every other project child.
- **Deriving completion from the result fields conflated two independent facts.** An orchestrator can close a session with no decisions recorded (changed their mind mid-session) and can fill in both result fields while the session is still open. Completion must be set explicitly, never inferred — which the v1.0 "both result fields null = incomplete" rule made impossible.
- **A three-value enum beats a boolean.** `pending` / `in-progress` / `finished` distinguishes "opened but not started" from "actively running," which a single `is_complete` boolean cannot express. Collapsing the retired boolean *and* the retired free-form label into one column removes the possibility of the two disagreeing.
- **The enum is fixed, not a dictionary, on purpose.** A session's lifecycle is an intrinsic, product-fixed property — unlike task/story statuses, which teams genuinely re-label per project. Making it configurable would invite a project to define statuses the "incomplete" query and the UI status control could not interpret. Validating a small fixed set at the schema layer (project-independent) keeps it out of the settings surface entirely, while reusing the established `"Value '{v}' is not allowed. Allowed: …"` 422 message shape so clients see one consistent validation convention.
- **No shipped data to migrate at design time.** The completion-model reversal was decided while the story was still `Pending Approval` on an unmerged branch — the domain had no released client or production data, paralleling the Milestones reversal (ADR-015). (The one running dev stack that had applied the earlier migration is a separate schema-drift matter handled outside this decision.)

**Trade-offs**:
- The Sessions shape diverges from the otherwise-LOCKED v1.0 contract, so readers must treat Sessions — like Milestones (ADR-015) — as a domain whose contract was revised (to v1.8). Documented explicitly in `docs/api-contract.md`.
- Session status is the one lifecycle field in the app that is *not* project-configurable. A future need to re-label or extend session statuses would require a code + contract change, not a settings edit — accepted, since the lifecycle is deliberately fixed.
- Enforcing no transition order (`finished` → `pending` is allowed) means the store records whatever the caller sets and never guards the lifecycle — consistent with this app's "stores facts, never enforces process" principle, but it places any workflow discipline on the caller, not the server.
- `status` validation lives at the schema layer while `participant_role` validation lives in the service (it needs a per-project dictionary lookup) — two different validation homes for two fields on the same entity, which a reader must not mistake for an inconsistency.
