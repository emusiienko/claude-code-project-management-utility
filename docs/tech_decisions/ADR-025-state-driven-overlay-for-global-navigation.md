# ADR-025: State-driven slide-over overlay for global Projects and Config navigation

**Date**: 2026-07-22
**Status**: Accepted

**Decision**: Make **Projects management** and **system Config** state-driven slide-over overlay panels layered over the always-mounted main view, rather than full-page routes. They have **no dedicated URL**. An always-mounted overlay host in the root shell owns a single overlay stack (`none` | Projects | Config); the top-bar Projects and Config entries are **triggers** (not `NavLink`s) whose active indication reflects overlay state, not route matching. The Projects overlay is a two-level stack — the project list (root) and one project's Settings (pushed on selection); Config is a single level (the system dictionary editor). The panel reuses the Story slide-over chrome (right-side panel, dimmed backdrop below the top bar, slide-in animation) and registers with the shared `useModalEscape` stack. Two controls: **Back** pops one internal stack level (shown only when depth allows), **Dismiss** clears the whole stack and reveals the unchanged main view underneath. A **forward bridge** ("Open in Task Manager") on a project's Settings panel navigates the main view to that project's Stories and dismisses the overlay in one action.

Consequently, the `/projects`, `/settings`, and `/projects/:projectId/settings` route entries are removed; per-project sub-navigation is reduced to three tabs (Stories, Board, Milestones — Settings leaves the tab set); and the app-switcher derives its mode purely from the current route. Cold start with no projects lands on an empty Task Manager main view with the Projects overlay auto-opened; with a project available it resolves to that project's Stories as before.

This decision revises — but does not wholly supersede — ADR-014. ADR-014's core still governs: the app-switcher, the three-level nested shell (`RootLayout` → `AppShell` → `ProjectShell`), the route-backed Story Detail slide-over, and the `RootRedirect`/last-visited-project mechanism are unchanged. ADR-025 changes only how Projects and Config are surfaced (overlays, not routes), retires the four-tab sub-nav's Settings tab, and makes Config global (both modes) instead of the Task-Manager-only `⚙ Settings` button ADR-014 described. ADR-014 remains `Accepted` because the majority of its decision is still in force.

**Options Considered**:
- **Routed pages with browser-history Back** (STORY-022 Revision 1) — `/projects`, `/settings`, and a standalone `/projects/:id/settings` screen, with `navigate(-1)` as the return affordance.
- **Routed pages with an explicit "close to last main view" model** (Revision 2) — a main-view/closable-view route classification, an always-mounted hook recording the last main-view URL in local storage, close affordances navigating to that recorded URL, and an app-switcher that derived its mode from the recorded URL while a closable view was open.
- **State-driven slide-over overlay with no URL** (Revision 3 — chosen).

**Rationale**: The two routed approaches both unmounted the active main view (Task Manager or Sessions) when Projects or Config opened, then spent increasing machinery trying to reconstruct where to return: `navigate(-1)` (unreliable, history-depth-dependent), then a whole classification/recording/derivation apparatus. BUG-006 was the same defect wearing a different face — the standalone Project Settings page had no live main view behind it, so a first visit to an unopened project was a dead end for reaching its Stories/Board/Milestones. Treating Projects and Config as overlays over a never-unmounted main view eliminates the return-target problem at the root: closing a panel reveals exactly the view that was always underneath, with its URL untouched. There is nothing to record or restore, and BUG-006 becomes impossible by construction (a live main view is always behind the panel; the "Open in Task Manager" bridge serves the one genuine forward need). The pattern also reuses conventions the app already had — the Story slide-over chrome and the `useModalEscape` stack — rather than inventing new navigation primitives.

**Trade-offs**: Projects and Config are no longer addressable or deep-linkable, and a page refresh closes the overlay and lands on the main view (the expected behavior for a modal surface, but a change from the routed model where those URLs were bookmarkable). Overlay state lives in client memory (owned by `RootLayout`, threaded to `TopBar` and the overlay host as props, reaching the one routed descendant via React Router's `<Outlet context>`), so it is not shared or persisted. This is the third navigation model shipped for the same surface within one story; a future engineer must resist re-introducing routed `/projects` / `/settings` pages — the whole point of this decision is that those surfaces are deliberately un-routed. The overlay must out-rank every other main-view surface in z-index (above the Task Detail modal and its nested dialogs, below the top bar and toast — BUG-007), which couples its stacking to the app's full z-index ladder rather than the Story slide-over's simpler two-layer assumption. Reverting to routed pages would again require rewriting the routing and shell composition, the same hard-to-reverse property ADR-014 carried.
