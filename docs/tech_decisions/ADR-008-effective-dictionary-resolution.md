# ADR-008: Effective-dictionary resolution — override fully replaces, never merges; derived, never stored

**Date**: 2026-06-30
**Status**: Accepted
**Decision**: A project's effective value for a dictionary key is resolved per key: if a `project_settings` row exists for `(project_id, key)`, its value list is used **in full** as the effective value; otherwise the `system_settings` value for that key is used. The project override **wholly replaces** the system default for that key — the two lists are never merged, deduplicated together, or concatenated. Effective settings are **derived on demand** at read time (`resolve` for one key, `resolve_all` for all six) and **never persisted** as a third row set. Setting an override for one key never touches other keys; clearing one key's override never touches others. This is the single resolution rule every future dictionary-bound domain (Story, Task, Task Link, Attachment) calls before any dictionary-validated write, via the `EffectiveDictionary` protocol exposed by the Settings service.
**Options Considered**:
- Replace semantics (chosen) vs merge/union of system default + project override
- Derived-on-demand resolution (chosen) vs a stored, materialized effective-settings row set kept in sync on every write
**Rationale**: Replace semantics are predictable and auditable — the orchestrator sees exactly the list a project will validate against, with no hidden inheritance to reason about. Merge semantics would make it impossible to *remove* a system value at the project level (you could only add), which defeats the purpose of a per-project vocabulary. Deriving on demand keeps a single source of truth (system row + optional override row); a materialized effective set would introduce a synchronization burden and a class of staleness bugs on every system-default change. Resolution is a cheap two-table lookup, well within the read-latency targets, so materialization buys nothing.
**Trade-offs**: A project that wants "system defaults plus one extra value" must restate the entire list as an override, not just the delta — accepted, because explicitness is the goal. Every dictionary-bound write in later domains incurs a settings resolution; this is a small, indexed lookup and acceptable for a single-machine tool.
