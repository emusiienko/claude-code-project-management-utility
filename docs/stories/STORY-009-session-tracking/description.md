# STORY-009: Session Tracking

## Desired Outcome
Working sessions between the orchestrator and an agent can be recorded within a project. Each session captures what the session was about (topic, goal, and context), its current lifecycle status (`pending`, `in-progress`, or `finished`), an optional result (decisions and summary), and two independent optional links — to a story and/or to a task — within that project. Sessions that were started but not yet finished (`status` is `pending` or `in-progress`) are discoverable in a single query scoped to the active project — even after a server restart — so an orchestrator agent never loses track of pending work in that project.

## Context
Sessions provide cross-restart continuity. When an orchestrator agent starts a new Claude Code session, it queries for unfinished sessions to know whether any prior working sessions (within its current project) are awaiting a result. A session's lifecycle is tracked by a single required `status` field with exactly three fixed values — `pending` (the default at creation), `in-progress`, and `finished` — and never anything else. `status` is never inferred from `result_decisions`/`result_summary`: a session can reach `finished` with no decisions recorded at all (e.g. the orchestrator changed their mind mid-session and simply closed it), and can remain `pending` or `in-progress` even after both result fields have been filled in.

Every session belongs to exactly one project — a session is never created "just for its own sake" outside a project context. `linked_story_id` and `linked_task_id` are two entirely independent, optional fields: `linked_story_id` lets a session point at a specific story in the same project, and `linked_task_id` lets it point at a specific task in the same project. A session may set neither, either one alone, or both at once — one is never a substitute for the other, and neither is ever a substitute for the project scope, which is always present.

A session's start artifact is made of three distinct text fields, each answering a different question: `topic` is a brief, at-a-glance label for the session (what it's called); `goal` is the concrete purpose the session was created to accomplish — the answer an agent needs when it asks "why does this session exist, and what am I meant to get done in it?"; `context` is general background information — the broader situation the session sits in, not the objective itself. None of the three substitutes for another: a `topic` is not a short `goal`, and `context` is not a restatement of `goal`.

## Acceptance Criteria
- [ ] A session can be created with a required `project_id` (the project it belongs to), a required topic (1–500 chars), a required goal (1–500 chars — the purpose the session was created for), optional context text, a required `participant_role` (validated against the project's effective `participant_roles` dictionary), and two independent optional links within that same project — a story link (`linked_story_id`) and a task link (`linked_task_id`); either, both, or neither may be set. `status` is not an accepted creation field — every new session starts at `status: pending`
- [ ] A session's `topic`, `goal`, `context`, `status`, `participant_role`, `linked_story_id`, and `linked_task_id` can all be updated after creation, independently of the result fields. Omitting a field in an update leaves it unchanged. Sending `context`, `linked_story_id`, or `linked_task_id` explicitly as `null` clears it. `topic`, `goal`, `participant_role`, and `status` are all mandatory and cannot be cleared — sending any of them as `null` is rejected as a validation error — but each can be changed to a new value: `topic` and `goal` are re-validated as 1–500 chars, `participant_role` is re-validated against the project's effective `participant_roles` dictionary, and `status` is re-validated as one of `pending` / `in-progress` / `finished`, on every update. `status` may be changed to any of the three values regardless of its current value — no ordering or transition restriction is enforced
- [ ] A session's lifecycle is tracked by a single required `status` field with exactly three fixed values: `pending`, `in-progress`, `finished`. It defaults to `pending` at creation and is not accepted as a creation input — every session starts at `pending`. It can be changed to any of the three values via update, at any time, in any direction, independently of `result_decisions`/`result_summary`
- [ ] A session's result can be recorded by setting `result_decisions` and/or `result_summary` independently via update, at any time, in any combination — these fields are purely informational and never affect `status`; a session can be marked `finished` with neither set, and can remain `pending` or `in-progress` after both are set
- [ ] All sessions whose `status` is `pending` or `in-progress` (i.e. not yet `finished`), and that are not archived, **for a given project** can be retrieved in a single query, scoped to that project; this query works correctly after server restarts. There is no cross-project variant of this query
- [ ] Sessions can be listed with pagination, always scoped to a single project — there is no cross-project session listing; archived sessions are excluded by default but retrievable with an explicit flag; results can optionally be filtered by `linked_story_id` to show only sessions linked to a specific story, and by an incomplete-only filter (`status` is `pending` or `in-progress`) — both combinable
- [ ] A session can be archived; archived sessions do not appear in default listings or in the unfinished-sessions query
- [ ] A session with neither a linked story nor a linked task is valid — the project link alone is sufficient

- Sessions are viewed and managed within the context of a single active project — consistent with the mandatory `project_id` scope, there is no cross-project Sessions view anywhere in the UI. Sessions is its own top-level app-switcher mode (alongside Task Manager), mirroring Task Manager's structure: it has its own project-selector sidebar and a nested Session Detail view scoped to the currently selected project — it is not a project sub-nav tab alongside Stories/Board/Milestones/Settings.
- **Sessions list**, scoped to the active project: shows topic, participant_role, linked story (clickable, shown separately) and linked task (clickable, shown separately), created_at, and a status indicator (`pending` / `in-progress` / `finished`) driven directly by `status`; supports an "incomplete only" filter (`status` is `pending` or `in-progress`), a filter by linked story, and pagination — the two filters are independently combinable
- **Create session**: a form capturing topic (required), goal (required — the purpose the session was created for), context, participant_role (required, selected from the project's effective `participant_roles` dictionary — a dropdown, not free text), and two independent optional link fields — a story link and a task link, each selectable from stories/tasks within the active project; either, both, or neither may be set. `project_id` is implicit — the active project — never a field the user fills in directly. Every session starts at `status: pending`; there is no `status` input on this form
- **Session Detail view**: a dedicated view, opened by selecting a session from the list, showing the full session record — topic, goal, context, status, participant_role, linked story, linked task, result_decisions, result_summary, created_at, updated_at. From here the user can edit every updatable field (topic — cannot be cleared, only changed to a new non-empty value —, goal — cannot be cleared, only changed to a new non-empty value —, context, participant_role — re-selected from the dictionary dropdown; cannot be cleared, only changed to another valid value —, linked story, linked task, result_decisions, result_summary, and a status control offering all three fixed values — `pending` / `in-progress` / `finished` — settable to any of the three at any time, in any direction) and archive the session
- Clicking the linked story, or the linked task, inside the Session Detail view navigates to that item's own detail view, consistent with the cross-linking conventions used elsewhere in the app (e.g. Story/Task links); the two links are independent navigation targets, shown and clicked separately
- Archiving a session is available both as a row action in the list and from within the Session Detail view

## Edge Cases & Error Scenarios
- [ ] A session's `status` can be set to `finished` with both `result_decisions` and `result_summary` still null — reaching `finished` never requires result content
- [ ] A session's `status` can remain `pending` or `in-progress` even after both `result_decisions` and `result_summary` have been filled in — `status` is only ever set explicitly, never inferred from result content
- [ ] A session's `status` can be moved to any of the three values from any of the other two, in either direction, at any time (e.g. `finished` back to `in-progress`, or `in-progress` back to `pending`) — no forward-only or blocked-transition rule is enforced
- [ ] Creating a session without a `project_id` is rejected as a validation error; creating one with a `project_id` that does not reference an existing project is rejected as not-found
- [ ] Linking a session to a story that does not exist is rejected with a not-found error; linking a session to a task that does not exist is rejected with a not-found error — the two links are validated independently
- [ ] Linking a session to a story that belongs to a **different** project than the session's own `project_id` is rejected as invalid; the same rule applies independently to a linked task
- [ ] A session linked to a story that is later deleted retains the session record; `linked_story_id` becomes null automatically
- [ ] A session linked to a task that is later deleted retains the session record; `linked_task_id` becomes null automatically — independent of, and unaffected by, the state of `linked_story_id`
- [ ] When a project is deleted, every session belonging to that project is deleted along with it
- [ ] Archiving an already-archived session is rejected: "Session is already archived."
- [ ] Creating a session without a `goal` is rejected as a validation error (422)
- [ ] Creating a session without a `participant_role` is rejected as a validation error (422)
- [ ] Creating or updating a session with a `participant_role` value that is not in the project's effective `participant_roles` dictionary is rejected: `422 "Value '{v}' is not allowed. Allowed: {list}."` — the same validation convention used for `default_web_ui_role` and task `assignee_role`/`creator_role`
- [ ] Creating a session with a `status` value in the payload is not a required behavior of this story either way (accept-and-ignore or reject are both acceptable; the architect decides) — but every newly created session ends up at `status: pending` regardless
- [ ] Updating a session with a `status` value outside the fixed set `pending` / `in-progress` / `finished` is rejected as a validation error (422): `"Value '{v}' is not allowed. Allowed: pending, in-progress, finished."` — reusing the same message convention as the dictionary-validated fields, even though `status` itself is a fixed enum, not a project dictionary
- [ ] Opening the Session Detail view for an archived session still shows its full record and keeps every updatable field editable — archiving does not restrict editing
- [ ] The Sessions list shows an explicit empty state ("No sessions yet") when the active project has no sessions — not an error
