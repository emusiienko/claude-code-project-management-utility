# STORY-009: Session Tracking

## Desired Outcome
Working sessions between the orchestrator and an agent can be recorded within a project. Each session captures what the session was about (topic, goal, and context), an optional result (decisions and summary), and an optional link to a story or task within that project. Sessions that were started but never concluded are discoverable in a single query scoped to the active project — even after a server restart — so an orchestrator agent never loses track of pending work in that project.

## Context
Sessions provide cross-restart continuity. When an orchestrator agent starts a new Claude Code session, it queries for incomplete sessions to know whether any prior working sessions (within its current project) are awaiting a result. A session's completion state is tracked by an explicit `is_complete` flag — it is never inferred from `result_decisions`/`result_summary`, since a session can be closed with no decisions recorded at all (e.g. the orchestrator changed their mind mid-session and simply closed it).

Every session belongs to exactly one project — a session is never created "just for its own sake" outside a project context. `linked_story_id`/`linked_task_id` are optional and additive: they let a session point at a specific story or task within that same project, but they are never a substitute for the project scope, which is always present.

A session's start artifact is made of three distinct text fields, each answering a different question: `topic` is a brief, at-a-glance label for the session (what it's called); `goal` is the concrete purpose the session was created to accomplish — the answer an agent needs when it asks "why does this session exist, and what am I meant to get done in it?"; `context` is general background information — the broader situation the session sits in, not the objective itself. None of the three substitutes for another: a `topic` is not a short `goal`, and `context` is not a restatement of `goal`.

## Acceptance Criteria
- [ ] A session can be created with a required `project_id` (the project it belongs to), a required topic (1–500 chars), a required goal (1–500 chars — the purpose the session was created for), optional context text, optional status (free-form string), a required `participant_role` (validated against the project's effective `participant_roles` dictionary), and optional links to a story (`linked_story_id`) or task (`linked_task_id`) within that same project
- [ ] A session's `topic`, `goal`, `context`, `status`, `participant_role`, `linked_story_id`, and `linked_task_id` can all be updated after creation, independently of the result fields. Omitting a field in an update leaves it unchanged. Sending `context`, `status`, `linked_story_id`, or `linked_task_id` explicitly as `null` clears it. `topic`, `goal`, and `participant_role` are mandatory and cannot be cleared — sending any of them as `null` is rejected as a validation error — but each can be changed to a new value: `topic` and `goal` are re-validated as 1–500 chars, `participant_role` is re-validated against the project's effective `participant_roles` dictionary, on every update
- [ ] A session's completion is tracked by an explicit `is_complete` boolean field. It defaults to `false` at creation and is not accepted as a creation input — every session starts incomplete. It can be set to `true` or back to `false` via update, at any time, independently of `result_decisions`/`result_summary`
- [ ] A session's result can be recorded by setting `result_decisions` and/or `result_summary` independently via update, at any time, in any combination — these fields are purely informational and never affect `is_complete`; a session can be marked complete with neither set, and can remain incomplete after both are set
- [ ] All incomplete sessions (`is_complete` is `false`, and not archived) **for a given project** can be retrieved in a single query, scoped to that project; this query works correctly after server restarts. There is no cross-project variant of this query
- [ ] Sessions can be listed with pagination, always scoped to a single project — there is no cross-project session listing; archived sessions are excluded by default but retrievable with an explicit flag; results can optionally be filtered by `linked_story_id` to show only sessions linked to a specific story, combinable with the incomplete-only filter
- [ ] A session can be archived; archived sessions do not appear in default listings or incomplete queries
- [ ] A session without any linked story or task is valid — the project link alone is sufficient

- Sessions are viewed and managed within the context of a single active project — consistent with the mandatory `project_id` scope, there is no cross-project Sessions view anywhere in the UI. Sessions is its own top-level app-switcher mode (alongside Task Manager), mirroring Task Manager's structure: it has its own project-selector sidebar and a nested Session Detail view scoped to the currently selected project — it is not a project sub-nav tab alongside Stories/Board/Milestones/Settings.
- **Sessions list**, scoped to the active project: shows topic, status, participant_role, linked story/task (clickable), created_at, and a completion indicator (complete / pending) driven directly by `is_complete`; supports an "incomplete only" filter (`is_complete = false`), a filter by linked story, and pagination — the two filters are independently combinable
- **Create session**: a form capturing topic (required), goal (required — the purpose the session was created for), context, status, participant_role (required, selected from the project's effective `participant_roles` dictionary — a dropdown, not free text), and an optional link to a story or task within the active project; `project_id` is implicit — the active project — never a field the user fills in directly. Every session starts incomplete; there is no `is_complete` input on this form
- **Session Detail view**: a dedicated view, opened by selecting a session from the list, showing the full session record — topic, goal, context, status, participant_role, linked story/task, result_decisions, result_summary, `is_complete`, created_at, updated_at. From here the user can edit every updatable field (topic — cannot be cleared, only changed to a new non-empty value —, goal — cannot be cleared, only changed to a new non-empty value —, context, status, participant_role — re-selected from the dictionary dropdown; cannot be cleared, only changed to another valid value —, linked story/task, result_decisions, result_summary, and a "Mark complete" / "Mark incomplete" toggle for `is_complete`) and archive the session
- Clicking a linked story or task inside the Session Detail view navigates to that item's own detail view, consistent with the cross-linking conventions used elsewhere in the app (e.g. Story/Task links)
- Archiving a session is available both as a row action in the list and from within the Session Detail view

## Edge Cases & Error Scenarios
- [ ] A session can be marked complete (`is_complete: true`) with both `result_decisions` and `result_summary` still null — completion never requires result content
- [ ] A session can remain incomplete (`is_complete: false`) even after both `result_decisions` and `result_summary` have been filled in — completion is only ever set explicitly via `is_complete`, never inferred from result content
- [ ] Creating a session without a `project_id` is rejected as a validation error; creating one with a `project_id` that does not reference an existing project is rejected as not-found
- [ ] Linking a session to a story or task that does not exist is rejected with a not-found error
- [ ] Linking a session to a story or task that belongs to a **different** project than the session's own `project_id` is rejected as invalid
- [ ] A session linked to a story that is later deleted retains the session record; `linked_story_id` becomes null automatically (same behavior for a deleted linked task and `linked_task_id`)
- [ ] When a project is deleted, every session belonging to that project is deleted along with it
- [ ] Archiving an already-archived session is rejected: "Session is already archived."
- [ ] Session `status` remains a free-form string, not validated against any dictionary
- [ ] Creating a session without a `goal` is rejected as a validation error (422)
- [ ] Creating a session without a `participant_role` is rejected as a validation error (422)
- [ ] Creating or updating a session with a `participant_role` value that is not in the project's effective `participant_roles` dictionary is rejected: `422 "Value '{v}' is not allowed. Allowed: {list}."` — the same validation convention used for `default_web_ui_role` and task `assignee_role`/`creator_role`
- [ ] Opening the Session Detail view for an archived session still shows its full record and keeps every updatable field editable — archiving does not restrict editing
- [ ] The Sessions list shows an explicit empty state ("No sessions yet") when the active project has no sessions — not an error
