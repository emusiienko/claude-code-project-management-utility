# Implementation Plan: STORY-022 — Global Project Navigation Entry

## Context
SESSION-018 (product-strategist) established that Project is the universal top-level anchor for every module in the utility — Tasks and Sessions today, any future module tomorrow — rather than a construct owned by or nested inside the Task Manager module. Today the only in-app path to the Projects management page (`/projects`) is the `⚙ Manage Projects` link buried in the Task Manager's collapsible left sidebar, which is invisible in Sessions mode and one level deeper than Settings (which sits directly in the always-visible top bar).

This is an interim, frontend-only story that relocates that single navigation entry to the persistent top bar so project management is reachable identically from any mode, ahead of a broader module-agnostic navigation redesign. It touches no backend, no API contract, and no data model.

A second, independent change was folded into this story during SESSION-020 (before implementation started): from the Projects Management page (`/projects`), clicking a project's name now lands on that project's **Settings** view instead of its **Stories** view — collapsing the "manage the project" and "configure the project" journeys into one entry point per project row. This is a landing-destination swap scoped to that single click target only; every other way of entering a project (notably the Task Manager sidebar) is unaffected and continues to land on Stories. No functionality is removed — Stories, Board, and Milestones stay reachable through the project's existing sub-navigation tabs once inside it.

**Refinement after TASK-003 shipped (2026-07-21).** TASK-003 retargeted the project-name click to `/projects/:id/settings`, but that route still rendered Project Settings as the fourth tab inside the per-project sub-navigation shell (Stories / Board / Milestones / Settings), so landing there looked like landing on a tab, not on a distinct destination. Project Settings is a project-configuration ("manage the project") concern reached from the Projects Management page — a management surface with no per-project tab chrome and no Task Manager sidebar. It is promoted to a standalone screen of its own, matching the existing standalone Milestone Detail screen (`/milestones/:id`): a top-level route with its own heading and a back-link to `/projects`, rendered outside the per-project sub-navigation shell. The project-name destination URL from TASK-003 (`/projects/:id/settings`) is unchanged; only where that URL renders changes. Consequently the per-project sub-navigation carries three tabs — Stories, Board, Milestones — and Settings is no longer among them.

## Revision 2 — 2026-07-21 (SESSION-021): closable-view navigation model
This revision reverses two decisions made earlier in this same story and adds a navigation model that TASK-001 through TASK-005 did not implement. It is captured here as the current design; the earlier task reports stay as the historical record of what those tasks shipped.

**Two reversals.**
1. **Config becomes global.** The original plan gated the Config (Settings) top-bar entry to Task Manager mode only and declared Settings visibility out of scope. The user now requires Config to be present in both main views, because system Config supplies dictionary values that Sessions also consumes (e.g. `participant_roles`). Config is therefore a persistent, always-visible, active-aware top-bar entry alongside Projects — the same treatment TASK-001 gave Projects. The invisible/disabled placeholder that kept Config mounted-but-hidden in Sessions (added to stabilise position, BUG-003) is no longer needed, since two always-present entries keep their positions by construction.
2. **Browser-history "Back" is replaced by "close to the last main view."** BUG-005 added a `navigate(-1)` Back button to the Projects page, mirroring the one Settings already had. The user rejects browser-history back as the wrong model: it returns the user to whatever URL happened to precede the current one, which is unreliable and history-depth-dependent. The intended model is explicit below.

**The mental model.**
- **Main views** are the app's two primary destinations: **Task Manager** (a project's Stories / Board / Milestones, including an open story slide-over or task modal) and **Sessions**. The app-switcher combobox chooses between them.
- **Closable views** are secondary surfaces layered over whichever main view is active: **Projects management** (`/projects`) and **system Config** (`/settings`). Closing a closable view always returns to the main view the user was in before opening it — regardless of how they got there or how deep the browser history is.
- **Project Settings** (`/projects/:projectId/settings`) is a sub-page of the Projects closable view, not a top-level closable view of its own. It keeps its existing fixed back-link to `/projects` (its single launch surface), unchanged by this revision.

**How "close to the last main view" works.** A component that is always mounted (the root layout / top bar region) observes route changes and, whenever the active route is a main view, records that full URL (path + query) as the "last main view" in browser local storage — the same persistence approach already used for the last Task Manager URL. Closable-view routes are excluded from this recording, so opening Projects or Config never overwrites the return target. Each top-level closable view's close affordance navigates to the recorded last-main-view URL; when nothing has been recorded yet (e.g. a cold load straight to `/projects`), it falls back to `/`, which the existing root redirect resolves to a Task Manager destination.

**App-switcher while a closable view is open.** The combobox reflects the underlying main view the user will return to (derived from the recorded last-main-view URL) rather than defaulting to Task Manager. Switching the combobox to the other main view navigates there, which also leaves the closable view. This keeps the switcher coherent when Config or Projects is opened from Sessions.

**Scope.** Frontend-only, consistent with the rest of this story — no backend, API contract, or data-model change. The global Config entry points at the existing `/settings` system-dictionary screen; making it reachable from Sessions requires no change to what that screen shows.

## Technical Approach
The persistent top bar (`RootLayout` → `TopBar`) is the only chrome present in every mode, so the global Projects entry lives there, in the right-side region alongside the existing Settings/Config action. The entry is a router-driven navigation link to `/projects`.

Active-page indication reuses the app's established pattern: a React Router `NavLink` whose `isActive` state drives both the visual highlight and `aria-current="page"` — the same mechanism used by the `ProjectShell` sub-nav tabs and the sidebar project list. This keeps the current-page behavior consistent with the rest of the app without introducing a new pattern. Keyboard focus uses the same `focus-visible` ring already applied to the top bar's controls.

Because the entry must be visible in both Task Manager and Sessions modes, the right-side region of the top bar must render unconditionally (today it renders only in Task Manager mode). The Projects entry is mode-independent — its presence, position, and behavior do not vary with the active mode or with route state (an open slide-over or task modal). Navigating to `/projects` is ordinary top-level router navigation, so any open Story slide-over or Task Detail modal is dismissed as a natural consequence of the route change — no special dismissal logic is required.

The second half of the change removes the now-redundant `Manage Projects` link (and its supporting sub-component / icon import) from the Task Manager left sidebar, so exactly one path to project management remains. The sidebar otherwise keeps the project list and collapse toggle unchanged.

Both halves land together as one atomic relocation: the AC "exactly one way to reach project management" is only satisfied when the entry is added in the top bar and removed from the sidebar in the same change.

**Project-name landing destination (separate module).** On the Projects Management page, each project-name entry navigates the user into that project. Today that navigation resolves to the project's Stories view; it must instead resolve to the project's Settings view. This is a self-contained change to the project-name click target in the Projects Management list — a different surface from the top-bar/sidebar relocation above. The two changes share the story but touch different modules and carry no dependency on each other. The change is scoped strictly to this one click target: the Task Manager sidebar's project selection (combobox and project list) keeps landing on Stories, and the router's default landing for a bare project URL is left as-is so the sidebar's behavior is untouched — the new destination is set explicitly at the click target rather than by moving the shared default.

**Project Settings as a standalone screen (refinement module).** Project Settings is promoted from a per-project sub-navigation tab to a standalone screen, reusing the pattern already established by the Milestone Detail screen (`/milestones/:id`): a top-level route rendered outside both the Task Manager sidebar shell and the per-project sub-navigation shell, with its own page heading (identifying the project by name) and a back-link that returns to the Projects Management page (`/projects`), its launch surface. Three moving parts, all frontend:

- The per-project sub-navigation is reduced to Stories, Board, and Milestones — Settings leaves the tab set.
- The `/projects/:id/settings` route is relocated so it renders the standalone Project Settings screen rather than tab content inside the sub-navigation shell.
- The Project Settings page gains standalone-screen chrome: a heading naming the project, a back-link to `/projects`, and its own handling of an unresolved project id (project-not-found / load-error states) — responsibilities the parent sub-navigation shell used to provide while Settings was a tab. The existing dictionary-override editor content is unchanged.

The project-configuration entry point is the project-name click on `/projects`; the back-link returns there, keeping the "configure the project" journey a self-contained loop distinct from the Task Manager "work the project" journey. The bare-project-URL redirect to Stories and the Task Manager sidebar behavior stay exactly as they are, so Stories/Board/Milestones remain reachable through the sub-navigation once inside a project via the sidebar.

## Constraints & Gotchas
- **Both modes, identical placement.** The top bar's right-side region currently renders only in Task Manager mode; it must render in both modes so the Projects entry is always present. The entry's position and behavior must not change between modes or when a slide-over/modal is open.
- **Settings visibility is out of scope.** *(Superseded by Revision 2 — Config is now global. This constraint reflected the original TASK-001 scope and no longer holds.)* The existing Settings/Config action stays gated to Task Manager mode as it is today — this story adds Projects only and does not change Settings' behavior.
- **(Revision 2) Config is a global top-bar entry.** Config sits beside Projects as a persistent, always-visible, active-aware entry in both main views, using the same `NavLink` `isActive` → `aria-current="page"` pattern and `focus-visible` ring as Projects. Two always-present entries hold their positions by construction, so the mounted-but-hidden placeholder from BUG-003 is retired.
- **(Revision 2) One "last main view" record drives every close.** An always-mounted component records the full main-view URL (path + query) on each main-view route change and skips the closable-view routes (`/projects`, `/settings`, `/projects/:id/settings`) so the return target survives the overlay visit. Reuse the existing last-Task-Manager-URL local-storage approach rather than introducing a new persistence mechanism. Close affordances read this record and fall back to `/` when it is empty.
- **(Revision 2) Closable views are `/projects` and `/settings` only.** Project Settings (`/projects/:id/settings`) is a sub-page of the Projects closable view and keeps its fixed back-link to `/projects` unchanged — do not point it at the last-main-view record.
- **(Revision 2) App-switcher tracks the underlying main.** While a closable view is open, derive the combobox's selected main from the recorded last-main-view URL, not from the closable-view path, so opening Config or Projects from Sessions keeps the switcher on Sessions.
- **Reuse the existing active-page pattern.** Use React Router `NavLink` `isActive` → `aria-current="page"` plus the existing top-bar `focus-visible` ring, matching `ProjectShell` tabs and the sidebar project list. Do not invent a new active-state or focus mechanism.
- **No manual dismissal logic.** Dismissal of an open Story slide-over or Task Detail modal on navigation to `/projects` falls out of normal router navigation — do not add bespoke close handling for it.
- **Full removal of the sidebar link.** Remove the `Manage Projects` link along with any sub-component and icon import that exist solely to support it; leave the project list and collapse toggle untouched.
- **Existing tests assert the old behavior.** `TopBar.test.tsx` (Settings button by mode) and `ProjectSidebar.test.tsx` ("Manage Projects link" / "still present when empty") encode pre-STORY-022 expectations and must be brought in line with the new behavior in TASK-002.
- **Landing-destination change is scoped to one click target.** Only the project-name click on the Projects Management page moves to Settings. The Task Manager sidebar's project selection must continue to land on Stories, and the router's default landing for a bare project URL must stay unchanged — set the new Settings destination explicitly at the click target, do not repoint the shared default. Verify the sidebar's Stories landing still holds after the change.
- **No functionality removed by the landing swap.** Stories, Board, and Milestones remain reachable via the project sub-navigation tabs once inside the project; this change only alters where the project-name click first lands. A project with no settings overrides lands on its Settings view showing values inherited from system defaults — that pre-existing inherited state is unaffected.
- **Standalone Settings mirrors Milestone Detail.** Model the standalone Project Settings screen on the existing `/milestones/:id` screen: a top-level route with a heading and a back-link, living outside both the sidebar shell and the sub-navigation shell. Reuse the project-existence check the sub-navigation shell performs today (the same hook it uses) so an unresolved project id still yields a not-found state now that the shell no longer wraps this route.
- **Preserve the bare-URL redirect and the top-bar active-state fix.** The bare `/projects/:id` redirect to Stories and the Task Manager sidebar's Stories landing stay unchanged. The top-bar Projects entry keeps its exact-match active state (BUG-001, resolved via the `end` prop) so a `/projects/:id/settings` URL — still under the `/projects` prefix — does not falsely mark the top-bar entry as the current page.
- **Settings entry point is the project-name click.** With Settings out of the sub-navigation, the project-name click on `/projects` is the single route to Project Settings, and the back-link returns there. This is intentional, matching the story's collapse of "manage" and "configure" into one entry point per project row.
- **TASK-004 refines TASK-003, does not undo it.** TASK-003's retarget to `/projects/:id/settings` stands; TASK-004 only changes how that URL renders. TASK-003's test coverage (project-name click resolves to that URL) remains valid and is re-guarded in TASK-005.
